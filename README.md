# Учёт успеваемости студентов — вариант 8

**Текущая версия: 0.4.0**

## 1. Описание проекта

Веб-приложение для учёта успеваемости студентов, разработанное на Python с использованием Flask и PostgreSQL.

Система предназначена для хранения информации об учебных группах, студентах, дисциплинах, учебных планах и оценках.

Проект разрабатывается в рамках дисциплины «Методология и практики DevOps» и последовательно проходит этапы проектирования, разработки, развёртывания, автоматизированного тестирования, контейнеризации и непрерывной интеграции.

### Основные возможности

- Управление учебными группами.
- Учёт студентов.
- Управление учебными дисциплинами.
- Формирование учебных планов.
- Выставление и хранение оценок.
- Просмотр средней успеваемости студентов.
- Регистрация и авторизация пользователей.
- Разграничение доступа к операциям изменения данных.
- Проверка работоспособности приложения и доступности базы данных.

### Основное бизнес-правило

Оценку студенту можно выставить только в том случае, если соответствующая дисциплина включена в учебный план его группы на указанный семестр.

Допустимые оценки: от 2 до 5.

## 3. Архитектура проекта

Приложение развёртывается на двух виртуальных машинах с Ubuntu Server без графического интерфейса.

| Сервер | Назначение | IP-адрес |
|---|---|---|
| APP-сервер | Flask-приложение в Docker | 192.168.40.135 |
| DB-сервер | PostgreSQL в Docker | 192.168.40.136 |

Основные сетевые порты:

- 5000 — веб-приложение и HTTP API.
- 5432 — PostgreSQL.

Приложение взаимодействует с базой данных через отдельного пользователя PostgreSQL.

### Компоненты приложения

- `app.py` — Flask-приложение, HTTP API, веб-интерфейс и авторизация.
- `domain.py` — бизнес-правила и проверка входных данных.
- `migrations/` — миграции базы данных.
- `lr3_tools/` — инструменты администрирования, проверки миграций, резервного копирования и восстановления.
- `tests/` — автоматические тесты.

### Аутентификация

Для доступа к системе предусмотрены регистрация и авторизация пользователей.

Используются сессионные cookies. Пароли хранятся в виде хешей.

Изменение данных через веб-интерфейс и защищённые API-операции доступно только авторизованным пользователям.

Начальный администратор создаётся командой:

```bash
flask --app app init-admin
```

Пароль передаётся через переменную окружения `ADMIN_PASSWORD`.

## 6. Локальная разработка и проверки

Для подготовки окружения используется единый сценарий установки зависимостей.

### Требования

- Python 3.12.
- PostgreSQL 16.
- Git.
- Docker и Docker Compose для контейнерных проверок.

### Установка зависимостей

```bash
make setup
```

### Основные команды Makefile

| Команда | Назначение |
|---|---|
| `make setup` | Подготовка виртуального окружения и установка зависимостей |
| `make run` | Локальный запуск приложения |
| `make quality` | Проверка форматирования, линтинг и Bandit |
| `make test` | Запуск автоматических тестов и формирование отчётов |
| `make migrate` | Применение миграций |
| `make migration-check` | Проверка миграций |
| `make backup` | Создание резервной копии |
| `make restore` | Восстановление резервной копии |
| `make backup-check` | Проверка резервного копирования и восстановления |
| `make mutation` | Контролируемое мутационное тестирование |
| `make container-check` | Проверка контейнерного окружения |
| `make verify` | Полный набор обязательных проверок |

Для подключения к PostgreSQL используются переменные окружения:

- `DB_HOST`
- `DB_PORT`
- `DB_NAME`
- `DB_USER`
- `DB_PASSWORD`

Для запуска приложения дополнительно используются:

- `SECRET_KEY`
- `ADMIN_PASSWORD`
- `APP_VERSION`
- `PORT`

**Важно:** автоматические проверки должны выполняться на выделенных тестовых базах данных. Использовать рабочую базу приложения для тестирования запрещено.

### Полный цикл локальной проверки

```bash
make setup
make verify
```

Команда `make verify` последовательно выполняет проверки качества кода, тестирование, миграции, резервное копирование и восстановление, мутационное тестирование и проверку контейнеров.

## 7. Контейнеризация и развёртывание

Для приложения и PostgreSQL используются отдельные Docker Compose-конфигурации.

### APP-контейнер

- Python 3.12 Slim.
- Запуск через Gunicorn.
- Два рабочих процесса.
- Непривилегированный пользователь UID 10001.
- Read-only файловая система.
- Ограничения CPU, памяти и количества процессов.
- Отключение дополнительных Linux capabilities.
- Docker Secrets для передачи конфиденциальных данных.
- Healthcheck через HTTP endpoint `/health`.

### DB-контейнер

- PostgreSQL 16.15.
- Постоянное хранение данных через Docker Volume.
- Healthcheck через `pg_isready`.
- Ограничения ресурсов.
- Docker Secrets для передачи паролей.

### Развёртывание PostgreSQL

На DB-сервере необходимо подготовить:

```text
secrets/
├── postgres_password.txt
└── db_password.txt
```

Запуск:

```bash
sudo docker compose -f compose.db.yaml up -d
```

### Развёртывание приложения

На APP-сервере необходимо подготовить:

```text
secrets/
├── db_password.txt
├── secret_key.txt
└── admin_password.txt
```

Запуск:

```bash
sudo docker compose -f compose.app.yaml up -d --build
```

Проверка состояния:

```bash
sudo docker compose -f compose.app.yaml ps
```

Проверка работоспособности:

```bash
curl -i http://192.168.40.135:5000/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

## 9. Непрерывная интеграция (ЛР5)

Для автоматизации проверки изменений используется **GitHub Actions**.

Основной workflow:

`.github/workflows/ci.yml`

CI Pipeline выполняет проверки автоматически и выступает обязательным барьером перед включением изменений в основные ветки и публикацией Docker-образа.

### 9.1. Условия запуска

Workflow запускается при:

- Push в `main` и `develop`.
- Push в feature-ветки.
- Push в release-ветки.
- Создании и обновлении Pull Request в `develop` и `main`.
- Ручном запуске через GitHub Actions.

### 9.2. Этапы CI Pipeline

**1. Code Quality**

Проверка качества и безопасности исходного кода:

- Ruff format.
- Ruff check.
- Bandit.

Используется:

```bash
make quality
```

**2. Automated Tests**

Запуск автоматических тестов с использованием отдельного PostgreSQL 16.

Создаются изолированные тестовые базы:

- `devops_test`
- `devops_lr3_clean`
- `devops_lr3_upgrade`
- `devops_lr3_restore`

Используется:

```bash
make test
```

**3. Database Checks**

Проверка миграций, резервного копирования, восстановления и контролируемых мутаций.

Используются:

```bash
make migration-check
make backup-check
make mutation
```

**4. Security Audit**

Проверка безопасности проекта:

- Gitleaks — поиск секретов в репозитории и Git-истории.
- pip-audit — проверка Python-зависимостей на известные уязвимости.

**5. Container Checks**

Проверка Dockerfile, Docker Compose, Docker Secrets, ограничений ресурсов и настроек безопасности.

Используется:

```bash
make container-check
```

**6. Build and Image Scan**

После успешного прохождения обязательных проверок:

1. Собирается Docker-образ.
2. Выполняется анализ с помощью Trivy.
3. Проверяются уязвимости уровней HIGH и CRITICAL.
4. Проверенный образ сохраняется как GitHub Actions Artifact.

Неисправленные уязвимости, для которых пока нет доступного исправления, исключаются из блокирующей проверки Trivy.

**7. Publish Docker Image**

Публикация в Docker Hub разрешается только после успешного прохождения всех обязательных этапов CI.

Публикация выполняется при Push в `main`.

### 9.3. Тегирование Docker-образов

Каждый опубликованный образ получает тег, связанный с SHA коммита.

Формат:

```text
DOCKERHUB_USERNAME/devops-app:COMMIT_SHA
```

Использование тега `latest` запрещено.

Для публикации используется тот же Docker-образ, который прошёл сканирование Trivy. Повторная сборка перед публикацией не выполняется.

### 9.4. Сохранение отчётов

GitHub Actions сохраняет результаты проверок:

| Файл | Назначение |
|---|---|
| `junit.xml` | Результаты тестирования |
| `coverage.xml` | Покрытие кода |
| `htmlcov/` | HTML-отчёт покрытия |
| `bandit.json` | Результаты Bandit |
| `pip-audit.json` | Результаты аудита зависимостей |
| `trivy-image.json` | Результаты сканирования Docker-образа |

Отчёты сохраняются в GitHub Actions Artifacts.

### 9.5. Кэширование зависимостей

Для ускорения CI используется кэширование pip через `actions/setup-python`.

Кэш зависит от файла `requirements-dev.txt`.

### 9.6. Защищённые переменные

Для авторизации в Docker Hub используются GitHub Actions Secrets:

- `DOCKERHUB_USERNAME`
- `DOCKERHUB_TOKEN`

Реальные пароли и токены не хранятся в репозитории и не передаются в открытом виде.

### 9.7. Защита критических файлов

Для контроля изменений критических файлов используется `CODEOWNERS`.

Владельцы назначаются для:

- Исходного кода приложения.
- Автоматических тестов.
- `Makefile`.
- Настроек анализаторов.
- Docker-конфигураций.
- CI/CD workflow.
- Правил приёмки проекта.

Для веток `main` и `develop` предусматриваются правила защиты GitHub:

- Обязательное создание Pull Request.
- Обязательное прохождение CI.
- Согласование изменений критических файлов.
- Запрет Force Push.
- Запрет удаления защищённых веток.

### 9.8. Контрольные испытания

Для подтверждения корректной работы CI предусматриваются испытания:

- Намеренное нарушение автоматического теста.
- Добавление фиктивного секрета.
- Проверка блокировки неуспешного Pull Request.
- Проверка отсутствия публикации Docker-образа после ошибки.
- Проверка согласования изменений критических файлов.

Все отрицательные испытания выполняются во временных ветках и не попадают в основные ветки проекта.

## 10. Git-процесс и правила приёмки

Для разработки используется GitFlow-подобная модель работы с ветками.

Основные ветки:

- `main` — принятая версия проекта.
- `develop` — интеграционная ветка разработки.

Дополнительные ветки:

- `feature/*` — разработка отдельных функций.
- `release/*` — подготовка новой версии.
- `hotfix/*` — исправление критических ошибок.

### Порядок внесения изменений

1. Создание задачи.
2. Создание feature-ветки от актуального `develop`.
3. Реализация изменений.
4. Выполнение локальных проверок.
5. Создание осмысленных коммитов.
6. Отправка ветки в GitHub.
7. Создание Pull Request в `develop`.
8. Автоматическое выполнение CI.
9. Проверка изменений и согласование.
10. Слияние Pull Request.

Для выпуска версии используется release-ветка, создаваемая от `develop`.

После повторных проверок создаётся Pull Request из release-ветки в `main`.

Прямой Push в `main`, Force Push и переписывание опубликованной истории запрещены.

Подробные правила находятся в [docs/RULES.md](docs/RULES.md).
