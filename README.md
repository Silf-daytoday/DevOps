# Система учёта успеваемости студентов

## Описание проекта

Система предназначена для учёта успеваемости студентов в рамках учебного процесса.

Приложение позволяет хранить информацию о студентах, учебных дисциплинах и полученных ими оценках.

Проект разрабатывается в рамках лабораторных работ и используется для отработки полного процесса разработки программного обеспечения:

- постановка задачи;
- создание отдельной ветки;
- разработка функциональности;
- локальная проверка изменений;
- работа с Git;
- создание Pull Request / Merge Request;
- автоматическая проверка через CI;
- выпуск версии приложения.

Основная цель первой лабораторной работы — разработать минимально работоспособное приложение с HTTP API, реляционной базой данных и настроенным Git-процессом.

---

# Предметная область

Предметная область проекта — учёт успеваемости студентов.

Система должна обеспечивать хранение следующих данных:

- сведения о студентах;
- сведения об учебных дисциплинах;
- сведения об оценках студентов;
- связь оценки со студентом и дисциплиной.

В дальнейших версиях проекта система может быть расширена поддержкой:

- учебных групп;
- учебных планов;
- семестров;
- преподавателей;
- экзаменов и зачётов;
- расчёта среднего балла;
- формирования ведомостей;
- статистики успеваемости.

# Назначение системы

Система предназначена для автоматизации базового учёта успеваемости студентов.

Основные функции приложения:

1. Добавление студентов.
2. Просмотр списка студентов.
3. Получение информации о конкретном студенте.
4. Добавление учебных дисциплин.
5. Просмотр списка дисциплин.
6. Выставление оценки студенту.
7. Изменение выставленной оценки.
8. Просмотр оценок конкретного студента.
9. Проверка корректности передаваемых данных.
10. Проверка работоспособности приложения через служебный HTTP-адрес.

# Основные сущности

В первой версии проекта используются три основные связанные сущности:

1. Student — студент.
2. Discipline — учебная дисциплина.
3. Grade — оценка.

Связь между сущностями:

Student 1-----N Grade N-----1 Discipline

Один студент может иметь несколько оценок.

Одна дисциплина может содержать оценки нескольких студентов.

Каждая оценка относится к конкретному студенту и конкретной дисциплине.

---

# Сущность Student

Содержит информацию о студенте.

Основные поля:

| Поле | Тип | Описание |
|---|---|---|
| id | integer | Уникальный идентификатор студента |
| full_name | string | ФИО студента |
| group_name | string | Название учебной группы |

Пример:
```
{
  "id": 1,
  "full_name": "Щеблыкин Константин Евгеньевич",
  "group_name": "241-351"
}
```
Ограничения:

- full_name не может быть пустым;
- group_name не может быть пустым;
- id формируется автоматически.

---

# Сущность Discipline

Содержит информацию об учебной дисциплине.

Основные поля:

| Поле | Тип | Описание |
|---|---|---|
| id | integer | Уникальный идентификатор дисциплины |
| discipline_name | string | Название дисциплины |
| semester | integer | Номер семестра |

Пример:
```
{
  "id": 1,
  "discipline_name": "Методология и практики DevOps",
  "semester": 5
}
```
Ограничения:

- название дисциплины не может быть пустым;
- номер семестра должен быть положительным целым числом;
- номер семестра должен находиться в установленном диапазоне.

---

# Сущность Grade

Содержит информацию об оценке студента по дисциплине.

Основные поля:
| Поле | Тип | Описание |
|---|---|---|
| id | integer | Уникальный идентификатор оценки |
| student_id | integer | Идентификатор студента |
| discipline_id | integer | Идентификатор дисциплины |
| value | integer | Значение оценки |

Пример:
```
{
  "id": 1,
  "student_id": 1,
  "discipline_id": 1,
  "value": 5
}
```
Ограничения:

- студент должен существовать;
- дисциплина должна существовать;
- значение оценки должно быть положительным целым числом;
- значение оценки должно находиться в допустимом диапазоне;
- для стандартной пятибалльной системы допустимы оценки от 2 до 5.

# Обработка ошибок

Приложение должно корректно обрабатывать ошибочные запросы.

## 400 Bad Request

Используется при передаче некорректных данных.

Пример:
```
{
  "detail": "Invalid request"
}
```
---

## 404 Not Found

Используется, если запрашиваемый объект отсутствует.

Например:
```
GET /students/999
```
Ответ:
```
{
  "detail": "Student not found"
}
```
---

## 409 Conflict

Может использоваться при попытке создать уже существующую запись.

Например, если студенту уже выставлена итоговая оценка по данной дисциплине.

Пример ответа:
```
{
  "detail": "Grade already exists"
}
```
---

## 422 Unprocessable Entity

FastAPI может автоматически возвращать данный статус при нарушении схемы входных данных.

Например:
```
{
  "value": 10
}
```
если разрешены только оценки от 2 до 5.

# Pull Request / Merge Request

После завершения задачи ветка отправляется в удалённый репозиторий:
```
git push -u origin feature/students
```
После этого создаётся Pull Request или Merge Request в ветку:
```
main
```
Перед слиянием необходимо убедиться, что:

- код запускается;
- тесты проходят;
- анализаторы не сообщают об ошибках;
- CI завершился успешно;
- изменения проверены другим участником команды.

# CI

Проект должен автоматически проверяться при отправке изменений в репозиторий.

CI выполняется при:

- push;
- создании или обновлении Pull Request / Merge Request.

Основные проверки CI:

1. Установка зависимостей.
2. Запуск автоматических тестов.
3. Запуск статического анализа.
4. Проверка корректности проекта.

Пример последовательности:
```
Git push
   ↓
CI
   ├── install dependencies
   ├── pytest
   └── ruff check
```
Изменения не должны объединяться с основной веткой при неуспешном CI.

---

# Правила внесения изменений

Для всех участников проекта действуют единые правила.

1. Все результаты работы хранятся в одном Git-репозитории.
2. Каждая новая функция разрабатывается в отдельной ветке.
3. Каждая задача должна содержать несколько осмысленных коммитов, если объём изменений это позволяет.
4. Перед отправкой изменений необходимо выполнить локальную проверку.
5. Изменения объединяются через Pull Request / Merge Request.
6. Необходимо проверять результат работы CI.
7. Запрещается удалять тесты для прохождения проверки.
8. Запрещается отключать анализаторы ради успешного CI.
9. Запрещается искусственно снижать требования к качеству кода.
10. Секретные данные не должны попадать в Git.
11. Файл .env не должен храниться в репозитории.
12. Критические файлы проекта должны изменяться через отдельные задачи и проходить проверку.
13. Основная ветка должна содержать работоспособное состояние приложения.
