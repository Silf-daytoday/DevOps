# Правила внесения изменений

1. GitFlow: задача → feature/* от актуального develop → несколько осмысленных
   коммитов → Pull Request в develop. Если develop отсутствует, он создается от
   актуального main; существующие ветки не перезаписываются.
2. Перед push обязательны успешные `python check.py` или `make verify` на отдельной
   PostgreSQL-базе devops_test. После переноса на PostgreSQL набор должен пройти
   дважды подряд. Статическая проверка не заменяет интеграционную.
3. При отсутствии доступной тестовой PostgreSQL изменения можно подготовить
   локально; push откладывается до фактических результатов. Запрещено объявлять
   проверки успешными без запуска, удалять их или ослаблять ради публикации.
4. Приемка: просмотр diff, успешные проверки, демонстрация браузера, /health,
   systemd, прав, firewall и остальных пунктов docs/LR2.md на ВМ. Для выполнения
   ЛР2 одним человеком допускается документированная самостоятельная проверка;
   она не называется ревью второго участника.
5. После приемки: release/0.2.0 от develop, финальная версия 0.2.0 и повторные
   проверки; PR в main и обратное слияние в develop. Тег v0.2.0 относится к
   принятому коммиту main. Старый тег v0.1.0 сохраняется без перемещения.
6. Запрещено коммитить env с секретами, ключи, файлы БД, дампы, venv, pycache;
   пушить напрямую в main, делать force push и переписывать опубликованную историю.
7. app.py, schema.sql, check.py и Makefile изменяются через PR. SQL основной базы
   не должен удалять рабочие данные; проверки не должны подключаться к ней.
8. Пароли вводятся локально интерактивно, а настройки службы находятся вне кода.
   Приложение запускается от devopsapp, без root и прав CREATE в основной БД.
9. Статус «инструкция подготовлена» отличается от «развертывание проверено».
   В PR явно указываются команды, результаты и еще не выполненные проверки.
