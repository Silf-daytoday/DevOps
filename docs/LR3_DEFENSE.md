# ЛР3: сценарий защиты

Адреса и учётные данные — из внешней конфигурации стенда.
Рабочее приложение запускается systemd, проверочные команды — на APP
из ~/devops-lr3 с тестовыми DB_* и активированным .venv.

1. `make verify`. Объяснить: Ruff format --check, Ruff check, Bandit,
   pytest (unit + реальная PostgreSQL/API/web), JUnit/coverage,
   clean/populated migrations, backup/damage/restore, два мутанта.
   Любая ошибка останавливает команду.
2. `make mutation`: разрешение 6 и обход учебного плана обнаруживаются
   конкретными unit-тестами. Рабочие файлы не меняются.
   Если преподаватель меняет условие в domain.py вручную, pytest должен упасть;
   после восстановления условия снова запускается полный verify.
3. `make migration-check`: чистая схема, заполненная ЛР2 без alembic_version,
   проверенный baseline, сохранение записей и обновление до head.
   Показать каталог migrations/versions и таблицу alembic_version тестовой БД.
4. `make backup-check` и ручной пример из раздела 8 docs/LR3.md:
   исходное имя LR3-CONTROL → LR3-DAMAGED → восстановленное LR3-CONTROL.
5. Открыть reports/junit.xml, reports/coverage.xml и reports/htmlcov/index.html.
   Объяснить разницу: процент Python-кода и доля функций ТЗ.
   Матрица учитывает отсутствующие Update/Delete и ролевые ограничения честно.
6. Показать комментарий к новой оценке через браузер и старые сохранённые данные.
7. Git: Issue → feature → проверки → PR develop → release → main/develop → тег.

Короткие ответы:
- Unit-тест проверяет чистое правило без сети и БД.
- Интеграционный тест проверяет Flask/SQL/ограничения PostgreSQL совместно.
- Миграция — версионированное изменение схемы; upgrade применяет изменения.
- Baseline отмечает только проверенную исходную схему, не создаёт её повторно.
- Backup — копия; restore проверяет фактическое восстановление данных.
- SAST анализирует исходники без запуска приложения.
- Venv изолирует Python-зависимости, тестовые БД изолируют данные.
- Runtime devops_app не выполняет миграции; локальный администратор
  делает DDL от devops_owner.
- У старых оценок неизвестная дата остаётся NULL; новая дата создаётся БД.
- Порог покрытия/анализаторы не ослабляются ради зелёного результата.
