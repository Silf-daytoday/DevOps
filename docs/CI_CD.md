\# CI/CD — Лабораторная работа №5



\## 1. Общая информация



Для реализации непрерывной интеграции используется GitHub Actions.



CI является обязательным этапом проверки изменений перед их включением

в основные ветки проекта и публикацией Docker-образа.



Workflow расположен в:



`.github/workflows/ci.yml`



\## 2. Условия запуска



Автоматический запуск осуществляется при:



\- Push в main и develop;

\- Push в feature/\* и release/\*;

\- Создании и обновлении Pull Request в develop и main;

\- Ручном запуске через workflow\_dispatch.



\## 3. Этапы CI Pipeline



\### Code Quality



Выполняется:



\- Ruff format --check — проверка форматирования;

\- Ruff check — проверка качества Python-кода;

\- Bandit — статический анализ безопасности.



Используется команда:



`make quality`



\### Automated Tests



Запускается отдельный PostgreSQL 16.



Создаются изолированные тестовые базы:



\- devops\_test;

\- devops\_lr3\_clean;

\- devops\_lr3\_upgrade;

\- devops\_lr3\_restore.



Выполняются автоматические тесты и формируется отчет покрытия.



Используется команда:



`make test`



\### Database Checks



Выполняются проверки миграций, резервного копирования,

восстановления и контролируемых мутаций.



Команды:



\- make migration-check;

\- make backup-check;

\- make mutation.



Все операции выполняются на тестовых базах данных.



\### Security Audit



Используются:



\- Gitleaks — поиск секретов в репозитории;

\- pip-audit — проверка Python-зависимостей на известные уязвимости;

\- Bandit — статический анализ Python-кода.



При обнаружении критических проблем pipeline завершается ошибкой.



\### Container Checks



Проверяются:



\- Непривилегированный пользователь;

\- Healthcheck;

\- Docker Secrets;

\- Ограничения CPU и памяти;

\- Запрет privileged;

\- Отсутствие секретов в Docker build context;

\- Конфигурации Docker Compose.



Используется:



`make container-check`



\### Build and Image Scan



После успешного завершения обязательных проверок:



1\. Собирается Docker-образ.

2\. Выполняется анализ Trivy.

3\. Проверяются уязвимости уровня HIGH и CRITICAL.

4\. Проверенный образ сохраняется как GitHub Actions Artifact.



Образ передается следующему этапу без повторной сборки.



\### Publish Docker Image



Публикация разрешена только при:



\- Push в main;

\- Успешном завершении всех обязательных проверок;

\- Успешном сканировании образа Trivy.



Образ публикуется в Docker Hub.



Формат тега:



`DOCKERHUB\_USERNAME/devops-app:COMMIT\_SHA`



Тег latest не используется.



\## 4. Отчеты



Сохраняются следующие отчеты:



| Отчет | Содержание |

|---|---|

| junit.xml | Результаты тестирования |

| coverage.xml | Покрытие кода |

| htmlcov | HTML-отчет покрытия |

| bandit.json | Результаты Bandit |

| pip-audit.json | Результаты проверки зависимостей |

| trivy-image.json | Результаты анализа Docker-образа |



Отчеты проверок сохраняются на 14 дней.

Архив собранного Docker-образа хранится 1 день.



\## 5. Кэширование



Для ускорения CI используется встроенный pip cache

действия actions/setup-python.



Кэш зависит от requirements-dev.txt.



\## 6. Защищенные переменные



Для подключения к Docker Hub используются GitHub Actions Secrets:



\- DOCKERHUB\_USERNAME;

\- DOCKERHUB\_TOKEN.



Реальные пароли и токены не хранятся в Git-репозитории.



\## 7. Защита критических файлов



В .github/CODEOWNERS определены владельцы:



\- исходного кода;

\- тестов;

\- Makefile;

\- настроек анализаторов;

\- Docker-конфигураций;

\- CI/CD workflow.



После завершения финального Pull Request для main и develop
будут настроены следующие правила защиты веток:



\- Обязательный Pull Request;

\- Обязательное согласование;

\- Обязательные проверки CI;

\- Запрет Force Push;

\- Запрет удаления защищенных веток.



\## 8. Соответствие локальным проверкам



Локальная команда:



`make verify`



выполняет те же основные проверки, которые используются в CI.



GitHub Actions запускает отдельные команды Makefile,

чтобы результат каждого этапа был виден в интерфейсе GitHub.



\## 9. Контрольные испытания



Для проверки отказоустойчивости CI используются временные

тестовые изменения:



\- Намеренно ошибочный тест;

\- Тестовый секрет;

\- Попытка изменения критического файла.



Такие изменения не включаются в основную ветку.



Ожидаемый результат:



\- Ошибочный тест приводит к остановке CI;

\- Gitleaks обнаруживает тестовый секрет;

\- Неуспешные проверки блокируют сборку и публикацию;

\- Изменения критических файлов требуют согласования владельца.



\## 10. Результат



GitHub Actions обеспечивает автоматизированную проверку

качества, тестирования, миграций, резервного копирования,

безопасности и контейнерного окружения.



Публикация Docker-образа выполняется только после успешного

прохождения всех обязательных проверок.
