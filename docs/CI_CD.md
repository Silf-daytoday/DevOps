# CI/CD — Лабораторная работа №5

## 1. Общая информация

Для реализации непрерывной интеграции используется GitHub Actions.

CI является обязательным этапом проверки изменений перед их включением в основные ветки проекта и публикацией Docker-образа.

Основной workflow расположен в:

`.github/workflows/ci.yml`

### Условия запуска

Workflow автоматически запускается при:

- Push в `main` и `develop`;
- Push в `feature/*` и `release/*`;
- Создании и обновлении Pull Request в `develop` и `main`;
- Ручном запуске через `workflow_dispatch`.

Для отмены устаревших запусков используется механизм `concurrency`.

## 2. Этапы CI Pipeline

Pipeline разделён на семь отдельных заданий.

### 2.1. Code Quality

Проверка качества и безопасности исходного кода.

Используются:

- Ruff format — проверка форматирования Python-кода;
- Ruff check — статический анализ и проверка стиля;
- Bandit — статический анализ безопасности Python-приложения.

Для выполнения проверок используется команда:

```bash
make quality
```

Результаты Bandit сохраняются в `reports/bandit.json`.

### 2.2. Automated Tests

Запуск автоматических тестов с использованием отдельного экземпляра PostgreSQL 16.

В процессе подготовки создаются изолированные тестовые базы данных:

- `devops_test`;
- `devops_lr3_clean`;
- `devops_lr3_upgrade`;
- `devops_lr3_restore`.

Для тестирования создаются временные учётные данные, которые не содержат реальных паролей проекта.

Используется команда:

```bash
make test
```

Формируются отчёты:

- `reports/junit.xml` — результаты тестирования;
- `reports/coverage.xml` — покрытие кода;
- `reports/htmlcov/` — HTML-отчёт покрытия.

### 2.3. Database Checks

Проверка работы миграций базы данных, резервного копирования и восстановления.

Выполняются:

```bash
make migration-check
make backup-check
make mutation
```

Все операции проводятся на тестовых базах данных.

Этап проверяет корректность миграций, возможность создания резервных копий, восстановления данных и устойчивость проверок к контролируемым изменениям.

### 2.4. Security Audit

Автоматизированная проверка безопасности репозитория и зависимостей.

Используются:

- Gitleaks — поиск секретов и конфиденциальных данных в репозитории и Git-истории;
- pip-audit — проверка Python-зависимостей на известные уязвимости.

Для Gitleaks используется полная история репозитория (`fetch-depth: 0`).

Аудит зависимостей выполняется для `requirements-dev.txt`.

При обнаружении проблем, нарушающих установленные условия проверки, этап завершается ошибкой.

### 2.5. Container Checks

Проверка конфигурации контейнерного окружения.

Используется команда:

```bash
make container-check
```

Проверяются:

- Наличие Dockerfile и Docker Compose-конфигураций;
- Запуск приложения от непривилегированного пользователя;
- Наличие HEALTHCHECK;
- Использование Docker Secrets;
- Ограничения CPU и памяти;
- Ограничение количества процессов;
- Read-only файловая система;
- Запрет privileged-режима;
- Отсутствие секретов в Git и Docker build context;
- Корректность Docker Compose-конфигураций.

### 2.6. Build and Image Scan

Этот этап запускается только после успешного завершения предыдущих пяти заданий.

Последовательность действий:

1. Выполняется сборка Docker-образа.
2. Запускается сканирование с помощью Trivy.
3. Проверяются уязвимости уровней HIGH и CRITICAL.
4. Формируется JSON-отчёт.
5. Проверенный Docker-образ сохраняется в GitHub Actions Artifact.

Для сканирования используются типы уязвимостей `os` и `library`.

Параметр `ignore-unfixed` позволяет не блокировать сборку из-за уязвимостей, для которых пока отсутствует исправление.

Если обнаружена блокирующая уязвимость, этап завершается ошибкой.

### 2.7. Publish Docker Image

Публикация Docker-образа выполняется только при следующих условиях:

- Событие запуска — Push;
- Целевая ветка — `main`;
- Все шесть обязательных этапов завершились успешно.

Перед публикацией скачивается ранее собранный и проверенный Docker-образ.

Повторная сборка перед публикацией не выполняется.

Для авторизации используются GitHub Actions Secrets:

- `DOCKERHUB_USERNAME`;
- `DOCKERHUB_TOKEN`.

Образ публикуется в Docker Hub.

Формат тега:

```text
DOCKERHUB_USERNAME/devops-app:COMMIT_SHA
```

Использование тега `latest` запрещено.

## 3. Схема выполнения Pipeline

Первые пять заданий выполняются независимо друг от друга.

Сборка и сканирование Docker-образа начинаются только после успешного завершения всех пяти заданий.

Публикация зависит от успешного завершения всех проверок, включая Trivy, и дополнительно разрешена только при Push в `main`.

Таким образом, ошибка на любом обязательном этапе препятствует публикации Docker-образа.

## 4. Сохранение отчётов

GitHub Actions сохраняет результаты проверок в виде артефактов.

| Артефакт | Содержание | Срок хранения |
|---|---|---|
| `quality-reports` | Отчёт Bandit | 14 дней |
| `test-reports` | JUnit, Coverage, HTML Coverage | 14 дней |
| `security-reports` | pip-audit | 14 дней |
| `image-security-reports` | Trivy JSON | 14 дней |
| `docker-image-COMMIT_SHA` | Проверенный Docker-образ | 1 день |

Отчёты позволяют анализировать результаты CI без повторного запуска проверок.

## 5. Кэширование зависимостей

Для ускорения выполнения CI используется встроенный механизм кэширования pip через `actions/setup-python`.

Кэширование зависит от файла:

`requirements-dev.txt`

При изменении зависимостей создаётся новый кэш.

## 6. Защищённые переменные

Для подключения к Docker Hub используются GitHub Actions Secrets:

- `DOCKERHUB_USERNAME` — имя пользователя Docker Hub;
- `DOCKERHUB_TOKEN` — токен доступа Docker Hub.

Реальные пароли и токены не хранятся в Git-репозитории и не передаются в открытом виде.

Для работы Gitleaks также используется автоматически предоставляемый GitHub токен `GITHUB_TOKEN`.

## 7. Защита критических файлов

Для определения владельцев критических файлов используется:

`.github/CODEOWNERS`

Владельцы назначаются для:

- Исходного кода приложения;
- Автоматических тестов;
- Makefile;
- Конфигураций анализаторов;
- Docker-конфигураций;
- CI/CD workflow;
- Документации с правилами проекта.

После завершения финального Pull Request для веток `main` и `develop` будут настроены правила защиты GitHub.

Планируемые правила:

- Обязательное создание Pull Request;
- Обязательное согласование изменений;
- Обязательное прохождение CI;
- Запрет Force Push;
- Запрет удаления защищённых веток;
- Обязательное согласование изменений владельцами критических файлов.

До включения соответствующих правил в GitHub Settings наличие CODEOWNERS само по себе не гарантирует обязательного согласования.

## 8. Соответствие локальным проверкам

Для выполнения полного набора локальных проверок используется:

```bash
make verify
```

Команда последовательно выполняет:

1. Проверку качества кода;
2. Автоматические тесты;
3. Проверку миграций;
4. Проверку резервного копирования и восстановления;
5. Мутационное тестирование;
6. Контейнерные проверки.

GitHub Actions выполняет эти проверки отдельными заданиями, чтобы результаты каждого этапа отображались независимо.

## 9. Контрольные испытания

Для проверки отказоустойчивости CI предусмотрены следующие испытания:

- Намеренное нарушение автоматического теста;
- Добавление фиктивного секрета;
- Проверка блокировки неуспешного Pull Request;
- Проверка отсутствия публикации Docker-образа после ошибки;
- Проверка согласования изменений критических файлов после включения правил защиты.

Контрольные испытания выполняются во временных ветках.

Ожидаемые результаты:

- Ошибочный тест приводит к неуспешному завершению Automated Tests;
- Gitleaks обнаруживает тестовый секрет;
- Неуспешные проверки препятствуют сборке и публикации;
- После включения правил защиты изменения критических файлов требуют согласования владельца.

Тестовые изменения не включаются в `main` и `develop`.

## 10. Результат

GitHub Actions обеспечивает автоматизированную проверку качества исходного кода, функциональности приложения, миграций, резервного копирования, безопасности зависимостей и контейнерного окружения.

Публикация Docker-образа в Docker Hub выполняется только после успешного прохождения всех обязательных проверок.

Реализованный CI Pipeline позволяет обнаруживать ошибки до включения изменений в основную ветку проекта и снижает риск публикации неработоспособных или небезопасных сборок.
